### 100k nodes / 150k edges

| Operation | Before | After | Target | Status |
|---|---:|---:|---:|:---:|
| Full build | 749s | **3.4s** | <120s | PASS |
| Vector search | 5.4ms | **2.4ms** | <50ms p95 | PASS |
| Graph-aware find | 175ms | **33ms** | <200ms | PASS |
| `/graph.json` hot | 9.6s | **131ms** | <500ms | PASS |
| `/clusters.json` hot | 9.7s | **513ms** | <500ms | CLOSE |

The improvements came from correct SQLite usage—batching, transactions, FTS
bulk-skip, indexes, caching—not a storage-engine swap. The locked decision is to
keep SQLite through approximately 1M nodes; see
[DB-DECISION-MATRIX.md](../../.planning/intel/DB-DECISION-MATRIX.md).

## Deferred / reopen triggers

- **Louvain cold path:** 9.1s at 100k; hot materialized path covers current UI.
  Revisit incremental communities if cold >120s or RAM >50% host.
- **Filtered ANN metadata:** add sqlite-vec metadata columns only if type-filtered
  vector retrieval regresses.
- **Staged compressed publication / index modes / structural code projection:**
  useful CBM patterns not yet required by measured gates; add only when a real
  workload crosses current thresholds.
- **Storage backend:** reconsider only after a measured trigger in
  `DB-DECISION-MATRIX.md`; no candidate currently provides a maintained,
  embedded, local-first improvement over SQLite.
